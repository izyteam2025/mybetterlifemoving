# Playbook: new client site (kickoff, brand, live content, conversion layout, build lessons)

Part of the starter rules, moved out of CLAUDE.md so it loads only when a task needs it. CLAUDE.md still holds the rules that apply to every change and wins on any conflict.

## Recipes

### New client site
0. **Kickoff request, on day one, before any build work (Artem 30 Oct 2026).** First ask: does the client already have a live website? If yes, this is a replatform, not a greenfield build — read `docs/playbooks/migration.md` before any build work and run its baseline export (GSC coverage, rankings, backlinks, live titles/metas/schema) and URL map alongside the request below, so nothing gets asked without also capturing what the old site already has. If no, skip the migration-specific steps in that playbook; there is nothing to preserve. Then send the client one request for everything only they can give, and take whatever already exists from their live site and GBP first so they are only asked for what is missing:
   - **Certificates and licenses:** every license and certificate (name, issuing body, number), with a scan or a link to the public record.
   - **Partners:** companies they work with (home warranty companies, property managers, parts suppliers, associations), and whether each partner's logo may be shown.
   - **Brands they repair**, and any brand they do not take; logo files from their current site where it shows them.
   - **Reviews widget:** Trustindex account access or the widget id (a WordPress plugin widget cannot be reused), plus every review profile (Google, Yelp, Facebook).
   - **Real photos and video:** technicians at work, the team (first name and role for each, with consent to show it), finished jobs, the van, a 20 to 40 second phone video of a visit.
   - **Social profiles:** every live profile URL.
   - **Booking and leads:** scheduler link (Housecall Pro, ServiceTitan, GHL), GoHighLevel call-back webhook, texting number.
   - **Tracking:** GTM, WhatConverts and Clarity ids. Read them off the live site (page source and the GTM container at `googletagmanager.com/gtm.js?id=<GTM id>`), show them to the user to confirm, and put them in `site.tracking` on day one; if the client has no live site, ask the user for them. When GA4, Clarity or WhatConverts already load inside the GTM container, set only `gtmId`, so nothing loads twice. The scripts only run with `SITE_LIVE=1`, so previews never touch the client's analytics.
   - **Prices and offers** they confirm in writing.
   The request goes through the client's Pros Buddy Client Portal in Notion. Add a Client Input database to the portal (same schema as Roka's), with one row per item above (Kind Kickoff). The project manager (Anna) asks the client in their preferred channel and pastes the answers in. Files (logos, photos, video, certificates, the old WordPress export) go to the client's folder in the agency Google Drive, never through Notion: see `docs/drive-import.md` for the folder, and put its id in `docs/growth/drive.json`. Put the Notion IDs in `docs/growth/notion.json`. Log what came back and what is still missing; the gate warns for every empty item.
1. Create the repo from this template; name it after the client domain.
2. Run the site map first (`client-site-mapping`): services, cities (and counties if the client works by county), brands, CTA destination, redirects for every live URL that moves.
3. Fill `site.json` from the persona, research and GBP: NAP identical to the GBP, `umbrellaKeyword`, `targetCity` (plus `targetCityPages: true` and a `region` per city for a multi-market, multi-state client; see CLAUDE.md), `cta`, `stats`, `offers`, `fixedFacts`, `competitors`, `compliance`, the client's brand (see Brand identity below), GTM / WhatConverts / GHL form.

### Brand identity (keep the client's existing brand)
A new site keeps the client's brand unless the client asks for a redesign. Take it from the live site (logo file, CSS colour variables, computed fonts, button shape) and the client's brand folder, never from guesswork.
- Logo: the original vector file in `public/brand/`, plus a white version for the dark footer. In `site.json`: `"logo": { "src", "footerSrc", "width", "height", "headerHeight" }`. Favicon in `public/favicon.svg` (or `site.favicon`).
- `theme`: `primary` (links, dark bands), `heading` (heading colour, defaults to primary), `accent` (CTA buttons), `surface`, `text`, `muted`, `footer` (footer background), `radius` (cards), `buttonRadius` (`999px` for pill buttons), `h2Transform` (`uppercase` or `none`), `fontBody`, `fontHeading`, `fontHref` (stylesheet URL with `display=swap`). Keep a `_source` note saying where each value came from.
- Photos: use the client's real job and team photos. Never reuse AI-generated or stock people presented as staff or customers.
- White text on the accent colour must reach 4.5:1 contrast; if the brand colour fails, darken the button shade and note it.

### Live content rule (every site, Artem 28 Oct 2026)
Anything that can be live must be live, so the site never looks fake or goes stale.
- **Reviews: only a live reviews widget** (Trustindex Google widget, as on plumbing-united.com). Never paste review text into copy files. Set `site.reviewsWidget = { "provider": "trustindex", "id": "<id from cdn.trustindex.io/loader.js?<id>>" }`. Until the id exists, the reviews block shows the Google rating with a link to the real reviews (`site.googleReviewsUrl`), never quotes.
- **Map:** `site.mapEmbedUrl` is the Google Maps embed of the client's own GBP listing (Maps > Share > Embed); it renders on the contact page and the service area hub.
- **Booking:** embed the client's real scheduler (Housecall Pro, ServiceTitan, GHL) on the conversion page with `embed` in its copy file, and set `site.form.mode = "booking"` so no page carries a form that posts nowhere.
- **Numbers:** rating and review count in `site.json` come from the GBP and are refreshed at every content release.

### Conversion layout (every site, Artem 28 Oct 2026)
A site must look like a real local company, not a template. The templates render these blocks when the data exists:
- **Hero:** real photo of a technician at work (`site.media.hero`; service pages use `services.json` `image`), Google rating badge above the H1 (from `site.rating`, linking to `site.googleReviewsUrl`), one primary CTA plus the phone.
- **One featured offer** as a banner right after the numbers (`featured: true` in `site.offers`); other offers as one quiet line each. Never a wall of coupon cards.
- **Meet your technicians** (`site.team`: first name, role, real photo). Names here are client-approved and allowed (data-allow-names).
- **Video** (`site.video`: `youtubeId` or `mp4` plus `poster`, `vertical: true` for a 9:16 phone video): a short phone video of a real visit; the client's own social videos work well. Click-to-load, no page weight.
- **Recent repairs** gallery (`site.gallery`, captions naming the appliance; `services` tags filter it per service page).
- **Brands we repair** as logos (Artem 30 Oct 2026): `site.brandsWeRepair` (names, or `{ name, logo }`), shown greyscale at one size, with the independence line `site.brandsNote` always under them (the gate fails logos without it) and never "authorized". `npm run brand-logos` fills `public/brand-logos/` from the open Simple Icons set; any other logo goes in that folder as `<brand-slug>.svg|png|webp`, preferably the files the client's current site already uses. A brand without a logo file shows as an icon tile with its name. Heading from `site.brandsHeading`. Home, service pages and About.
- **Certificates and licenses** (`site.credentials`: name, issuer, number, and proof as `verifyUrl` or a scan in `image`): real ones only, from the kickoff request. Home, service pages and About; feeds `hasCredential` in the schema. The gate fails a credential without an issuer or proof. Hidden while empty.
- **Partners** (`site.partners`: name, logo with the partner's permission (an icon tile until then), url, note): home warranty companies, property managers, suppliers, associations. Never a manufacturer (the gate fails a partner that is also in `brandsWeRepair`). Home and About. Hidden while empty.
- **Membership / plan band** (`site.membership`) linking to its page; pages in `site.navExtra` count as conversion pages for the link rules.
- **Every city shown** in service area blocks; cities without a page yet appear as plain text.
- **What a visit costs** (`site.pricing`: heading, intro, items with label, value, note; client-confirmed numbers only) after the offers on every money page.
- **Call-back form** (`site.callback.webhookUrl`, the client's GoHighLevel inbound webhook): name and phone only, in the closing block and inside the booking overlay for people who give up on the scheduler. Hidden until the webhook exists.
- **"What's wrong?" picker** on the home page: appliance, then symptom, built from each live service page's problem cards; the choice travels with the call-back request.
- **ZIP checker** on the service area hub from `locations.json` `cities[].zips`; hidden until ZIPs exist.
- **Text button** in the mobile bar from `site.sms.e164` (the client's texting number); hidden until set.
- **Social profiles with icons (Artem 28 Oct 2026):** every profile the client has (`site.gbpUrl` plus `site.sameAs`: Google, Facebook, Instagram, YouTube, Yelp, Nextdoor, TikTok, LinkedIn, X) shows as an icon button in the footer and on the contact page, so the business looks active. Only real, live profiles; the same list feeds `sameAs` in the schema.
- **Agency credit:** the footer ends with "Created by ProsBuddy Agency" linking to prosbuddy.com (agency rule); `site.agencyCredit: false` removes it only if the client contract says so.
- **Booking overlay:** with `site.booking.url`, every Book button opens the client's scheduler on the page (no page hop); the conversion page embeds it inline.
- **Photos (Artem 28 Oct 2026):** every site starts with free stock photos (Pexels, Unsplash) marked `placeholder: true`, and they are swapped for the client's real photos in `public/photos/` (WebP, alt text) as they arrive. Real photos come in through the Drive import (`docs/drive-import.md`), which strips the GPS position and all other metadata; never commit a photo straight from a phone. Stock photos may go live; the build lists them as a warning. Previews show a "Sample photo" tag; with `SITE_LIVE=1` (set in Cloudflare Pages production when the client's domain is attached) the tag is hidden, a stock face is never shown as a named technician (that card shows the initial until the real photo arrives), and a sample video is hidden until the real one exists.

4. Fill `services.json`, `locations.json` (set `countyPages: false` for a cities-only map), `brands.json` (empty array when no brand pages), `authors.json`. Reviews come from the live widget (see Live content rule), not `reviews.json`.
5. Build `keywords.json` with DataForSEO: volume, keyword difficulty and the live SERP for each planned page. One primary per page.
6. Write copy with the agency skills, outputting into the JSON / Markdown formats above instead of Word: `homepage-copy`, `services-hub-copy`, `service-area-hub-copy`, `service-page-copy`, `county-page-copy`, `city-page-copy`, `city-service-page-copy`, `brand-page-copy`, `blog-content`. Keep every rule the skill defines.
7. Delete all demo content (Northline), replace `public/og-default.png` and `public/favicon.svg`.
8. `npm run build` until green, open a PR for Artem.
9. Launch checklist: every page fact-checked by a person (`factCheck` on each copy file, no fact-check warnings left), `SITE_LIVE=1` set in Cloudflare Pages production env (hides sample tags, stock team faces and the sample video), GTM / WhatConverts / Clarity ids set, Cloudflare AI bot setting, GSC and Bing Webmaster Tools verified (the service account is a Full user in Search Console, so the sitemap is submitted automatically after launch: `docs/search-console.md`), `INDEXNOW_KEY` set in GitHub secrets and Cloudflare env, redirects tested, `site.timezone` set, `CF_DEPLOY_HOOK` secret set (scheduled publishing), `GOOGLE_SA_KEY` secret and `docs/growth/drive.json` filled (client files import), `AUDIT_BASE_URL` variable removed so the live audit crawls the client domain, and the monthly growth scheduled task created — Claude does this automatically the moment the site goes live on its production domain, without waiting to be asked (prompt at the end of `docs/monthly-growth.md`).
10. **Add the client to the agency's 🧭 Client Cohort Registry in Notion** (Client, Repo, Domain, Cohort, Status "Active", Growth Day — usually 2, matching the monthly growth scheduled task above). The daily Watchdog and Dispatcher agents work off the GitHub org and ProsBuddy Agent's own client list and need no registry entry, but the **Lead SEO Agent monthly rollup reads this registry only** — skip this step and the new client's growth cycle runs but nobody notices if it doesn't.

### Build lessons (every site, Artem 28 Oct 2026)
Learned on live builds; they apply to every client. The gate cannot catch most of them, so the independent review checks them.
- **Prices:** publish only client-confirmed amounts, in the exact wording the persona or `site.fixedFacts` locks. Never a standalone fee the client has not approved. Cost pages show typical costs as national averages, each linked to a named, credible, non-competitor source, never as the client's price.
- **Local detail:** when the client files have no neighbourhoods or ZIPs, research them on the city's official site and Wikipedia, list every name with its source URL in `docs/local-detail.md` ("public research, to confirm with the client"), and use names only: no landmarks, distances, travel times or claims about who lives there. Never in the hero.
- **ZIP checker:** core ZIPs only: the ZIP's main post office city is that city, no PO-box ZIPs, none shared with cities outside the service area. The checker must never say yes to a place the client does not cover.
- **No operational claims the files do not state:** where technicians start from, appointment windows (opening hours are not appointment slots), procedures on the visit, "in-house" staff, portfolio sizes, brands beyond `site.brandsWeRepair`.
- **Never promise pages that are not live** ("each has its own page below"), and never show internal sources to customers ("on our Google Business Profile list").
- **Location pages are not templates with the city swapped:** no shared FAQ answers, H2s, closings or hero ideas between location pages; an audience angle is fine, but not stated as a local fact ("Lakewood families"); on city service pages, keep questions natural instead of stuffing the city into generic ones.
- **Locked wording is copied exactly** (late-arrival line, warranty as "90-day", never "ninety").
- **Launch scope:** the site map plans every page; the first launch is capped at 50, filled in this order: main architecture (home, hubs, main services, About, FAQ, Contact, booking, membership, legal), service area hub, city pages, city service pages (highest volume first; none for the target city), then blog. Finished pages over the cap wait in `content/drafts/` (lowest search demand first); the blog hub goes live with the first post or guide.
- **How a build runs:** research, then writers in parallel (each owns separate files, runs `npm run validate` only, and keeps FAQs page-specific), then one `npm run build`, then an independent reviewer who did not write the copy (facts against the files, duplication across location pages, voice: pet words, stock phrases and machine-like rhythm, rule breaks, UX at 390px and 1280px), then fixes, then the PR. Never a humanizer tool.
- **Outbound link check:** sources that block bots (401/403/429) are listed to check by hand; 404, 410, 5xx and timeouts fail.
